## 踩坑记录（复用价值）

- JMeter 元素注册名看 saveservice.properties：barrier 是 `SyncTimer` 不是 SynchronizingTimer；根元素是 `jmeterTestPlan`
- JMeter 容器堆：jmeter 脚本自带 HEAP="-Xms1g -Xmx1g"，覆盖用 HEAP 环境变量，传 JVM_ARGS 会初始>最大冲突
- CSVDataSet 一行一个值，逗号拼接单行=整行被当成一个变量（曾致 199×HTTP400）
- compose 相对路径（build context / 卷挂载）按 compose 文件目录解析，本仓库需 `../..`
- zsh 下 `rm xx*` 无匹配会中止整条命令；pkill 模式串会匹配自身命令行
- npm 必须 npmmirror 源（官方源 39KB/s 龟速）；容器内 node_modules 用命名卷隔离，避免 alpine(musl) 与宿主(glibc) 的原生二进制混装
- JMeter 元素注册名看 saveservice.properties；CSVDataSet 一行一个值

## 构建注意事项

- 打包必须加 `-Ddocker.skip=true`：fabric8 docker-maven-plugin 默认连远程 Docker `192.168.3.101:2375`（prod残留），不加会超时报错
- 完整命令：`mvn -pl mall-common,mall-mbg,mall-admin,mall-portal,mall-gateway,mall-auth -am package -DskipTests -Ddocker.skip=true`
- 改代码后的部署：`docker compose -f document/docker/compose-local.yaml up -d --build`（会重建应用镜像并滚动重启）
- compose 的 build context 是 `../..`（compose 文件在 document/docker/ 下两层深，曾踩坑写成 `..`）

## 2026-10-08 全组合阶梯取证与修正（16 相位 l2_*）

### 装置缺陷（已修复）
| 缺陷 | 根因 | 修复 |
|---|---|---|
| bulk_detail 全轮次 100% 错 | 采样器硬编码 id=100050，pms_product 最大 id=100045 → selectById null → NPE | 改 id=100044 |
| search_kw 测的不是搜索 | 参数名写成 k=w（keyword=null）；叠加 pageNum=0 bug | 改 keyword=压测&pageNum=1&pageSize=10 |
| 阶梯 -l/-j 路径容器内不存在 | 用了宿主机绝对路径，jmeter 容器解析不到 → 16 相位白跑 | 改容器挂载路径 /jtl/ |

### 真实缺陷发现
- **search 默认空列表（原作者 bug，两分支都有）**：`PmsPortalProductController.search` pageNum 默认 0 → PageHelper 对 pageNum<1 跳过数据查询只跑 count → total 正确但 list=[]。master 已修 `0→1`（commit 见 git log）；baseline-upstream 保持原样作对照。
- **abA 详情页确定性 500**：生成数据 product_attribute_category_id 为 NULL → 原生 Example `addCriterion` 抛 "Value cannot be null"；优化版 MP eq 容忍 null（空列表）→ 正常。零负载即可复现，与压力无关。
- **"B 总 TPS 低 3/4"是测量假象**：每线程每轮串行打 10 接口，圈速被最慢接口绑架；A 的 detail/bulk 快速失败使圈速虚高。分接口延迟才是有效指标。

### 瓶颈定位（多轮误判的教训）
- 排除项（实测证据）：磁盘无关（buffer pool 命中率 99.9996%，热数据 42MB/128MB）；MySQL 平均 0.31 核（被空闲分钟稀释的假象）。
- **真瓶颈：MySQL 1 核配额**。60 并发只读实测复现 7s 延迟：mysql CPU 101%（打满）、portal 掉到 25%（干等）。单条查询毫秒级，等的是队列。连接池（Druid max-active 20）在 DB 队列上二次排队。
- **教训：看瓶颈看活跃时段峰值，不看全程平均；结论必须用受控实验复现，不接受监控图直读。**

### 修正措施（均已生效）
1. compose：mysql cpus 1→2（挪走 DB 墙，让差异回到应用层）；portal/admin 维持 1c
2. Nacos（portal/admin dev.yaml）：datasource 下加 druid max-active=50（两变体共用同一份，公平）
3. master：search pageNum 默认 0→1
4. vt_ladder2.sh：每相位新增全容器资源采样（res_*.csv，5s 粒度，CPU/内存），报告脚本 mall-bench/l2_report.py 联合出矩阵

### 2026-10-08 第二轮取证（2c+修复装置后的 16 相位）

- **jtl 追加污染**：rm -f 误用容器路径 /jtl/（宿主不存在，静默失败）→ JMeter 对已存在 -l 文件追加，新旧两轮数据拼接、跨度 104 分钟、TPS 被摊薄 60 倍。修复：rm 改宿主路径；清洗=按最大时间间隙切段保留新段。教训：**容器路径只许出现在传给容器的参数里，宿主侧操作一律用宿主路径**。
- **资源记录器**：子 shell 漏了 `> $RES` 重定向，数据流到 stdout——从脚本日志按相位边界恢复成 res_*.csv 后修复重定向。
- **旗舰发现：pms_sku_stock 无 product_id 索引**（原版 schema 就没有）：30 万行后每次详情/批量详情的 SKU 查询 = 4016ms 全表扫，performance_schema digest 记账单条 SQL 总耗时 17208 秒居全场第一。**加 idx_product_id 后 ~5ms（800 倍）**。讽刺互证：abA 因"属性分类 null"bug 在第 3 步异常退出，走不到 SKU 查询——上游两个 bug 互相掩护；优化版修好前者才暴露后者。
- **次级发现**：LIKE '%kw%' 的 PageHelper count 均 788ms/次（无法建索引，固有成本）；portal 内存 1000c 时贴线 99.98%（511.9/512MiB）→ 配额提到 768m 防 OOM 污染相位。
- **方法论沉淀**：A/B 的 SQL 文本不同（Example 内联 vs MP 占位符）→ performance_schema digest 天然分开记账，`ORDER BY SUM_TIMER_WAIT` 直接定位单条烧 CPU 的 SQL——比看容器 CPU 曲线精确一个数量级。
- 索引加在共享 DB（两变体同享），A/B 代码差异保持干净隔离；索引属运行时夹具层，baseline-upstream 分支代码零改动。

### 2026-10-08 第三轮：写路径装置修复 + 协议修正

- **又发现一个原生缺陷：收藏服务检查-插入竞态**。collection_add 对 (memberId,productId) 先 findOne 再 insert，无原子性、Mongo 无唯一索引——并发下多请求同时通过存在性检查 → 插入重复文档 → 之后 findOne 抛 `returned non unique result` → HTTP 500。上一轮收藏阶梯 1243 请求 1243 错全由此来（固定 productId=27 热点键把竞态放大到必现）。修复装置后（productId 全域自增 + 相位间 Mongo 复位）该路径不再被触发，缺陷已记录、基线分支不改。
- **jmx 修复**：收藏 body 由固定 `{"productId":27}` 改 `${__counter(FALSE)}` 全局自增（20s×140TPS≈2800 << 10 万商品池，零重复=每发真实写）；ab_test_vt.sh 相位间 `deleteMany` 复位收藏集合。
- **协议修正（用户拍板）**：A=原生整套（代码+JDK17+SB3.5.14，无 VT 能力），不设 VT 变量；B=优化整套（JDK25+SB4.0.8+VT+索引+代码）。阶梯 16→12 相位（A 每档 1 相位、B 每档 VT 关/开 2 相位）；报告归因链 A → B·VT关（迁移+代码+索引收益）→ B·VT开（VT 收益 +29~65%）。历史 A 的 VT 开相位重新定性为重复性对照组（±4% 噪声标尺）。
- **方法论两条**：① 查能力先查 JVM 再查框架（JDK17 无 Loom，SB 属性存在也是 no-op）；② 对照组只设在真正存在自由度的维度上。
- 待办：T=1000 VT=true cart 相位曾出现 959×30s 超时（cart 数据仅 288 条，疑偶发，重跑验证中）。
